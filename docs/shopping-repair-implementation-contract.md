# 购物流程修复：统一实现约定 v2（设计依据）

本文在开始编码前形成，保留约定与设计依据；它本身不是测试报告。
起始版本的实测成绩为 53/60，后续实测另行记录，不因文档约定增加通过数。

后续更新：部分合同现已落地，实际实现范围与未完成项见
[v2 运行说明](shopping-v2-runtime.md)。本文保留设计依据，不能据此推定所有扩展已完成。

范围：修复已发现的单位表达、额外硬条件、条件替代和过滤后零候选恢复，
并接入“模型默认推荐后，再由专门模型解释数量”的流程。
前端、数据库并发事务和真实账户购物车写入不属于本轮实现。

## 1. 不变的默认顺序

```text
保存原话/上下文 → 提取结构化需求 → 必要时澄清阻碍搜索的信息
→ 程序搜索 → 模型候选语义审查 → 程序核验真实商品与硬约束
→ 模型默认推荐商品 → 专门模型解释购买件数 → 程序核验解释并计算报价
→ 用户确认整份方案/修改
→ 刷新商品事实 → 按目标购物车差量更新 → 最终验证
```

搜索结果多，不自动要求用户先选。只有无法可靠推荐、冲突/不确定，
或用户主动要求挑选，才进入候选选择分支。
未知数量不默认 1；用户已明确的数量不重复询问。
模型建议不是执行授权；语义判断不等于商品事实。

## 2. 唯一的数据来源与保存位置

会话保存 `schema_version=2`、不可变原始 instruction/household_context、
追加式 `intent_revisions`、全局 `budget_cents`、初始购物车、逐项需求、
待答问题、推荐版本、当前批准及过程记录。

预算由整篮统一计算，不复制成多项可独立放宽的额度。
真实商品资料只能来自工具，模型输出不得覆盖工具字段。

每项需求保存：

- `requirement_id`：稳定 ID，局部重试不改动其他需求 ID。
- `quantity_request`：kind、min/max、原始单位、原始表达、证据；未知数量为 null。
- `constraints`：有类型、有来源的持续条件，不能在缺货后自动删除。
- `primary`：首选 description/search_query、用户明确指定的 UPC（若有）和证据；
  区分用户指定的商品条件与模型在这些条件内挑选的 UPC，不能把模型选择升格为用户硬要求。
- `fallback`：null 或 trigger、替代范围/指定替代品、查询目标、条件及授权证据。
- `phase=primary|fallback`：当前生效规则；不与执行进度混用。
- `status`：当前执行进度，包括 unresolved、selected、needs_quantity、added 等。
- `selected_product_id`、逐项 selection_revision、当前数量解释与所绑定商品事实版本。
- `candidate_history`、`availability_observations`、`explicit_exclusions` 及其来源/时间。

`active_requirement` 由程序从 phase、有效修订、持续条件和 primary/fallback 构造，
不是另一份可独立修改的意图。搜索、审查、推荐、数量解释、最终核查共用它。
历史首选仍可作为上下文，但不能在 fallback 阶段继续成为硬名称要求。

## 3. 证据与硬条件

证据保存来源（原话、上下文路径或用户修订）和原文 quote。
程序核对 quote 确实存在；有引用只是必要检查，不证明任意语义转换都正确。

条件类型固定分开：

- `description`：名称、形式、口味、包装等语义条件，交给语义模型审查并提供字段依据。
- `tag`：用户明确要求的标签，商品必须有对应显式证据，缺失保持 unknown。
- `nutrition`：营养数值条件，必须明确数值、单位和计量基准；不能自动制造阈值。

模型不允许把 No Salt Added 自动转为额外 low_sodium 标签。
支持的标签映射需显式注册；不受支持的真实用户要求保持为待解释/澄清条件，
不能静默删除。无来源条件或不受支持的推导先修复意图/澄清，不能直接将商品判无候选。
营养数值与标签是不同证据；不因存在某个钠数值就自行认证低钠。
tree_nut_free 不等于 nut_free；名称不能替代缺失的过敏证据。

## 4. 数量表示与专门模型解释

`quantity_request.kind` 区分 packages、contents、volume、weight、unknown。
原始单位和表达独立保留；未知不生成精确 min/max。
原话/上下文指定一盒半加仑商品时，保留包装数和包装要求，
不能由模型改成精确 1892 mL。真实总量要求则由程序按统一单位换算与精度规则核验，
不增加全局任意容差，不对某条 benchmark 加 1 mL 特判。

推荐 UPC 确定后，专门数量模型读取原话、有效需求、原始数量表达、
工具的原始规格/可信归一化字段、阶段和当前状态。
输出绑定 requirement_id、UPC、selection_revision，并使用四种结果：

- `proposal`：正整数 `purchase_packages`、外包装/内含解释、字段证据和不确定点。
- `conflict`：单位、包装或明确要求冲突；不能直接执行。
- `needs_clarification`：缺数量或解释需确认，提出具体到该商品的问题。
- `insufficient_product_data`：规格不足，不能猜包装/内含数量。

程序校验 ID、事实来源、证据、正整数和可信同量纲算术，不宣称能靠规则理解所有商品。
例如两瓶可乐配 12 罐装不能自动变成两组；两盒每盒 6 支冰淇淋不能解释为两支。
用户选择 UPC 本身不表示同意改变数量或包装形式。
商品变化使旧解释失效；用户明确的总量保留，对旧 UPC 确认的包装数不无条件转移。

## 5. 工具失败的分类和 phase 转换

工具适配层统一提供可供程序判断的 reason，而不是让模型猜错误原因：

- `confirmed_out_of_stock`：工具明确报告缺货或当前详情明确 in_stock=false。
- `insufficient_stock`：当前数量无法满足，但不证明库存为零；单独处理，不自动当作确认缺货。
- `service_error`：API/网络/鉴权/限流等，不能启用缺货替代。
- `invalid_product_data` / `constraint_conflict`：商品事实不足或条件不满足，不是缺货。
- `invalid_request`：调用参数错误，修复调用，不改变用户目标。

适配器可解释其自身稳定的商家/环境错误格式；核心状态机不依赖任意错误文本关键词。
无法确认失败原因时保持 unknown，不以确认缺货处理。

仅当当前 phase=primary、首选确认缺货且已有有效 fallback 时，程序切换到 fallback。
清除失败商品的选择和当前整篮批准，保存缺货观察，只重开受影响需求。
若改选需要改变用户明确条件且没有授权规则，返回 `needs_substitution_permission`；
无明确答复不自动改变条件。模型自选 UPC 缺货后，若其他商品仍满足全部原要求，
可在原范围内重新推荐，不必额外询问“是否允许替代”，但旧整篮批准失效，仍需确认新方案。
fallback 商品再次缺货时，在同一授权范围内恢复，不能再扩展范围或无限切换。

## 5.1 没有替代授权时的三种情况

1. 用户只说“买酸奶”，A 是模型推荐：A 缺货后可重新推荐仍符合原约束的 B，
   保持原需求范围/阶段，不伪造一条用户 fallback。用户确认新的整篮方案后再执行。
2. 用户明确指定 A，未说能否换：暂停受影响需求，保留其他商品。
   可整理具体替代建议并明确差异，询问是否接受；建议属于待批准信息，不能直接加购。
   若用户只授权“允许其他品牌”，先记录范围修订，再推荐/解释数量/展示整篮确认。
   若展示的已是完整可执行方案，用户明确接受可同时记录该项修订和该版方案确认，
   不重复询问同一个决定；仍执行确认后的事实刷新。
3. 用户明确说“只要 A，不接受替代”：保留这条限制，报告缺货并等待用户选择等待、
   明确取消该项或主动修改要求，不能自动替代，也不能自行删除需求后声称原任务完成。

所有情况都不把沉默当作同意，不因改选而自动放宽预算、数量或过敏条件。
提出建议可先读取商品事实，但模型不能把这种探索性建议当作已经生效的需求修订。

## 6. 搜索、审查和重试预算

初始实现采用以下统一上限，可在开发验证后版本化调整：

- 每项需求的每个阶段，一轮发现最多 3 个不同查询（初始查询加最多 2 个扩展查询）。
- 同一查询工具瞬时失败最多重试 1 次，仍计入总工具调用数。
- 同一次语义审查输出格式错误最多修复 1 次；服务错误不走语义修复。
- 查询按规范化字符串去重，阶段内重试有计数，暂停/恢复不能重置为无限预算。
- 保持模型/工具/时间总上限；不因新增步骤移除实验限制。

扩展查询同时覆盖 raw search=0 和语义审查/硬过滤后 eligible=0。
是否扩大检索要参考具体过滤原因，不因缺少过敏证据而放松条件。
primary 无候选不等于确认首选缺货，不能只因检索失败启用 fallback。
合格候选与 uncertain 候选分开保存，后者不能自动变为可执行商品。

## 7. 候选历史与局部恢复

explicit_exclusions 只保存用户明确拒绝，缺货观察和本轮未选不能写成永久拒绝。
历史商品再次被考虑或用户选回时，按当前需求重新读取价格、库存、规格和标签。
只为实际重新考虑的商品读取必要详情，避免遍历全部历史耗尽工具预算。
生成新版本 option_id，旧选项不能用来跳过当前检查。

部分商品已加入时保存实际购物车，按新目标计算差量，避免重复加入。
局部阶段变化不重置其他需求；整篮预算和批准仍必须重新计算。

## 8. 问题、方案版本与 API

每批待答问题保存 question_id、requirement_id、相关 UPC、selection_revision 和问题类型。
回答必须与当前待答问题匹配，验证整批后再修改状态。

`needs_substitution_permission` 的答复允许明确拒绝，或提交有范围的替代授权；
自然语言授权要解释并保留原文，单独的“同意”不能授权一个未定义的替代范围；
对已明确展示的具体替代方案答“同意”，只确认该具体方案，不扩大为无限制替代授权。
数量冲突答复需指向具体解释，不能把修改包装视为默认接受任意件数。
实际 HTTP JSON 字段在实现时按此合同统一，不并存互相矛盾的答案入口。

完整方案包含商品、包装、购买件数、预计总价和未解决问题。
只有全部需求有可执行解释且无待解决冲突，才能进入 awaiting_basket_confirmation。
用户可接受、改数量、换商品、追加限制；改动只使相关解释及整篮批准失效。
接受后再次刷新关键事实；变化后重新解释/报价并确认。

继续使用当前签名 checkpoint，新增 schema/阶段/规则/解释/问题版本和预算计数。
旧 checkpoint 保守兼容：没有保存的替代授权不能凭空补出，必要时要求新确认。
当前 checkpoint 内拒绝过期问题/方案；数据库并发锁与跨旧 token 的强重放防护不在本轮范围，
不得宣称无数据库状态已经保证真实账户写入的事务幂等。

## 9. 日志和验收顺序

过程分别保存：查询与结果身份、模型审查理由/证据、硬过滤原因、数量解释及校验结果、
工具失败类型、phase 转换依据、问题/答复版本、新草稿和最终状态。
不能只用 no_candidates/hard_constraints 代替具体诊断。

实施顺序：

1. 需求 schema、来源校验、active requirement、状态持久化与兼容。
2. typed 失败原因、逐项 phase 转换、原范围内重选/需要授权的变更之区分、
   无授权询问、过滤后零候选发现恢复。
3. 推荐后专门模型数量解释、条件类型校验、完整方案与重新确认。
4. API/模拟用户合同与回归测试，再运行真实模型实验。

先用离线控制流/反例测试验证边界，再复核 K06/K17、K16/K19 各表述及 K20 两次缺货，
然后完整重跑 60 条、新交互开发用例和实时演示，全部存入新目录。
冻结 benchmark 和评分器不因修复而改答案，代理不接触隐藏 UPC/评分条件。
模拟用户只用独立意图/授权档案答复，不能替模型修正错误商品、放宽硬目标或默认接受冲突。
开发反例覆盖不同商品，不能将只通过这些用例称为全部场景泛化。
