# 通用品类的模型推荐与数量解释：设计及实现边界

状态：支线聊天确认的设计约定，后续 v2 已实现部分主链。
实际能力、API 和限制见 [v2 运行说明](shopping-v2-runtime.md)；不代表下文所有扩展已完成。

最新设计修正：默认由模型推荐商品，再由专门的模型步骤解释购买件数，
然后展示完整方案让用户确认/修改。此前“用户先选商品，再判断数量”的默认顺序有误，
由本修正取代。候选选择只作为无法可靠推荐、冲突/不确定或用户主动要求挑选时的分支。

字段、错误类型、重试边界和问题/方案版本的统一实施依据见
[统一实现约定 v2](shopping-repair-implementation-contract.md)；其设计约定与实际能力需区分。

## 当前实现边界

当前已实现搜索零结果重试、独立候选语义审查（related / unrelated /
uncertain）、程序硬约束检查、选定 UPC 后询问缺失的包装数量，以及基于
已知 count / volume_ml / weight_g 的包装换算。
HTTP 的 recommend 模式请求 v2 意图，已接入推荐后的 ModelQuantityInterpreter，
保留原始数量表达、证据和逐项解释，并能暂停处理包装冲突及确认结构化数量修订。
旧 v1 会话保留兼容路径，不具备完整 v2 解释步骤。

仍未完成任意自然语言的通用 intent 修订、所有规格/精度的换算及未见商品泛化验收。
现有数量模拟用户不能作为这些语义能力全部正确的证据。
下文状态名称是建议设计，当前代码仍使用 selected/needs_quantity 等状态与会话边界。

## 目标与职责

让可乐、冰淇淋、牛奶、花生等不同商品共用同一套需求与包装解释流程，
避免为每个品类堆 if 或关键词规则，也避免把原话过早压缩成“买 N 个包装”。

- 模型负责候选语义审查与默认商品推荐，再由专门步骤解释推荐包装的购买件数、
  提出依据、不确定点或澄清问题；推断只是建议，不自动写购物车。
- 程序负责保存状态、验证 UPC 与字段证据、核验正整数件数和可信同量纲算术、
  价格/库存/硬条件、整篮总价与购物车差量，控制状态转换及调用工具。
- 用户负责确认完整方案、修改数量/商品/限制，以及确认歧义或是否接受明确要求的改变。
- 商家工具提供商品事实；模型不能生成商品事实或直接操作购物车。

## 推荐流程

1. 保存不可变的原始请求，另存用户后续明确修订。intent 区分明确事实、
   未知和可选偏好，并记录原话证据。例如“两瓶可乐”保存目标数 2 和原始
   单位“瓶”，不能只保存 quantity=2。
2. 只在缺失信息阻碍当前动作时询问。商品、数量、品牌、预算不能一概要求
   填满；通常可先搜索并由模型推荐包装，数量仍未知时再问。必要的过敏信息可以
   在安全搜索前询问。
3. 广泛搜索并保留原始商品资料及来源。归一化商品名、类别、UPC、价格、
   库存、外包装形式、内含件数、内含单位、重量/体积及显式标签；额外属性
   保留在可扩展 attributes 中。未知的包装事实不通过商品名称猜成已知。
   当前 Kroger 适配器主要覆盖杂货；其他商家需要独立的数据适配器。
4. 扩展独立候选审查：模型读取原话、当前 intent、修订和真实商品资料，
   返回 compatible / incompatible / uncertain、理由、引用字段及可能的
   解释或冲突。程序验证 ID 来自工具，并复核价格、库存、预算、显式标签
   等硬条件。不能默默改写用户要求，也不能把模型判断写回商家商品事实。
   这些建议术语与当前 related / unrelated / uncertain 的映射需在实现时明确。
5. 默认由模型结合当前有效需求审查并推荐一款或若干款最合适的商品，给出依据和
   不确定点。不能因为搜索有多款就默认让用户先挑。模型无法可靠推荐、存在冲突/
   不确定性或用户主动要求挑选时，才进入候选选择分支。每个推荐方案分别绑定具体 UPC。
6. 推荐商品确定后，调用专门的模型数量解释步骤，输入原话、数量/单位要求、
   推荐商品原始规格和当前状态，输出结构化解释及依据。模型可提出外包装购买数与
   内含总量，程序仅对可信同量纲数据作算术核对；选择或推荐 UPC 本身不代表
   用户已经接受数量、包装形式变化或购物车操作。
7. 展示完整推荐方案：商品、包装、建议购买件数、预计总价和任何冲突。
   用户可接受、改数量、要求换商品或提出新限制。解释不确定、商品形式冲突、
   数据不足或会改变原意时，先澄清或重新推荐，不能直接执行。
   答复绑定 question_id、requirement_id、商品和解释版本；保存为 intent revision，保留原话。
   修订影响商品或包装时，返回审查/推荐/数量解释，仅重开受影响需求。
8. 用户确认整份方案后，刷新实时库存、价格、规格与硬条件；关键事实变化则重算并
   重新展示确认。否则按确认的目标购物车和已有购物车差量更新，再最终验证。
   缺货、超预算和验证失败只重开受影响需求及整篮计算，等待期间保存可恢复状态。
   真实账户购物车写入与下单仍属另行授权的执行范围。

## 专门模型数量解释的合同

输入包括不可变原话和有效修订、原始数量表达与单位、当前生效需求/替代阶段、
推荐 UPC 的原始规格与可信归一化字段、来源、当前已确认状态。

v2 模型解释结果已区分以下四类；这些是解释结果，不与商品执行 status 混用：

- `proposal`：提出购买件数、对应外包装与内含总量、引用依据和不确定点。
- `conflict`：单位/包装/原意不兼容，明确冲突及改变购买方式的实际后果。
- `needs_clarification`：需要用户补充数量或确认某种解释，问题应具体到推荐商品。
- `insufficient_product_data`：商家规格不足以可靠解释，不能凭空补内含数量或包装事实。

结果绑定 requirement_id、推荐 UPC 和解释版本。可执行的购买件数必须为正整数，
原目标数量/单位与解释分开保存，不能提前把“两瓶”压成“两件 UPC”。
程序核对引用确实存在、数据来自工具、算术与可信字段相符；这些校验不等于
程序已能理解所有自然语言商品含义，不能用逐品类硬编码替代模型语义判断。
解释建议不能直接写入购物车，不能把模型推断写回商家事实。

## 必须支持的判例

- “两瓶可乐”推荐单瓶装：有可信包装依据时可建议买 2 件，展示具体包装和总价后确认。
- “两瓶可乐”推荐 12 罐装：瓶与罐不能直接换算。说明包装形式冲突，问
  是否改为罐装、买几组；绝不能自动买两组、得到 24 罐。
- “两盒冰淇淋”推荐每盒 6 支：可提出“买 2 盒，共 12 支”，不能解释成两支；需要确认
  用户是否接受这种形式。如果原话明确“桶装”，多支装商品不兼容。
- “12 个鸡蛋”推荐 6 个装：商品类型匹配、单位同为个且包装数据可信时，
  可建议 2 盒，由程序核对；无需重复问已明确的数量，但仍确认整篮方案。
- “2 升牛奶”推荐 1 升盒装：可建议 2 盒。“两瓶牛奶”推荐盒装则需要判断
  并确认是否接受包装形式变化。

## 建议保存的需求状态

```text
needs_search
→ candidates_reviewed
→ product_recommended
→ interpreting_quantity
→ awaiting_plan_confirmation
→ refreshing_product_facts
→ updating_cart
→ added
→ final_verification
→ complete
```

候选选择不是默认必经状态。`waiting_product_choice` 只在模型不能可靠推荐、
存在冲突/不确定或用户主动要求时进入。数量解释可返回澄清/冲突/资料不足分支，
用户修改后回到受影响需求的推荐或解释；事实变化后重新生成方案并确认。
上述是建议状态名，不取代当前已实现的 selected/needs_quantity 等枚举。

无候选、缺货、超预算属于可恢复分支。状态转换由程序根据结构化结果和
工具数据决定。单项需求至少保存原话证据、目标数及原始单位、推荐 UPC、
外包装/内含事实及来源、候选解释、待确认问题、解释版本和用户修订记录。

## 验证要求

使用开发时未见过的跨商品场景，分别统计错误自动换算、错误替代、应问
未问、无必要提问、约束违反、提问轮数和模型成本。上述判例只是开发约束，
不能代替未见场景评测；当前通过的测试与 benchmark 不证明本方案已完成。
还需验证默认先由模型推荐，再执行专门数量解释；多个搜索候选不会自动变成用户必答选择题。
确认前不写车，用户修改及事实变化会使旧方案失效，已有购物车不会重复添加。
