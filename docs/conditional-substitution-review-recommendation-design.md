# 条件替代、候选审查与整篮推荐：整合后的待实现方案

状态：支线聊天确认的后续实现依据；仅记录设计，未据此修改运行代码或冻结 benchmark，
不表示本方案已实现或已通过验收。

后续更新：v2 已接入部分主链和结构化接口，实际完成项及限制见
[v2 运行说明](shopping-v2-runtime.md)。上段描述记录时状态，不能覆盖后续实现状态。

本文将 [K16 缺货替代设计](k16-stock-fallback-design.md) 扩展到 K19、K20，
补齐候选审查、整篮推荐、用户确认与局部恢复之间的合同。
商品编号仅用于描述观察记录，不得写成场景或商品特判。

编码前的统一字段、错误类型、重试上限与问答版本约定见
[统一实现约定 v2](shopping-repair-implementation-contract.md)。该约定同样待实现，
用于避免各模块对当前需求和授权范围作不同解释。

## 1. 已观察到的三种失败路径

- **K16 high**：首选 Planet Oat Original UPC `0004410015618` 加车时缺货。
  程序只清除选择、回到 unresolved，仍用首选查询和混合需求描述。
  Extra Creamy、Unsweetened、Barista 等符合替代范围并具有必需标签的候选
  被判 unrelated；相似 Original 候选又缺少明确 nut_free，最终 no_candidates。
- **K19 medium**：Breakfast Blend 缺货后，Colombian UPC `0001111010741`
  已出现在搜索结果中，却被审查模型判 unrelated，理由是它是替代品而非所要求的 Breakfast Blend。
  支线复核发现 high/low 的提取描述恰好包含替换条款而成功，说明当前行为依赖模型措辞，
  并没有由程序可靠地控制规则何时生效。
- **K20 high/medium/low**：Penne 和 Marinara 分别触发缺货。
  第二轮审查认出 Ditalini 意面，但酱仍按 Marinara 查询。原查询返回 20 条，
  多数为意面，指定的 Tomato Basil 酱没有进入这批结果，最终 no_candidates。
  原有鸡蛋、面包及已加入胡萝卜保留。恢复时只应重开意面/酱，并重算整篮 $8 预算。

K16/K19 体现当前生效目标与候选判断不一致；K20 还体现检索漏召回。
不能将这些机制都笼统解释为“商店没有合格商品”。

## 2. 意图与会话状态

每项 requirement 分别保存：

- 不可变原话、相关上下文及证据片段；后续明确修订另存，不能覆盖原话。
- 数量目标、原单位及始终有效的硬约束；整篮预算仍由全局会话统一计算，避免逐项重复计入。
- `primary`：首选商品/名称、用户明确指定的 UPC（若有）、查询目标与来源。
- `fallback`：可空；保存启用条件、允许品类范围或指定替代品、持续硬约束、来源证据。
- `phase=primary|fallback`：该商品需求当前生效的规则阶段。
- `status=unresolved|selected|needs_quantity|added` 等：该商品需求的执行进度。
- 当前选中 UPC、历轮候选与展示时信息、库存观察、来源及时间。
- 用户明确排除与相应修订；本轮未选、暂时缺货不能混为永久拒绝。

phase 是每项商品自己的状态，与进度 status、全局购物车、整篮预算分开。
例如酱可处于 fallback，胡萝卜仍处于 primary/added，不必重置整个购物篮。

最初由 intent 模型从用户文本/上下文提取替代规则，程序验证来源并保存。
不得读取评分器隐藏允许 UPC，不得在缺货后由模型临时编造替代授权。
原话未授权改变明确条件时，保存 `fallback=null`，需要改变条件才询问是否允许及其范围。
如果原要求只限定品类等条件，具体 UPC 是模型自选，其他商品仍满足原要求，
则可以在原范围重新推荐，无须额外的替代授权题，但必须重新确认新版整篮。

## 3. 首选搜索与独立候选审查

初次 `phase=primary`，程序以首选目标调用 `search_products`。

`ModelDiscovery.review` 的输入：

- request：用户原话、上下文和有效修订；
- 当前生效的 `active_requirement`，包括 phase、目标、数量和硬条件；
- 工具实际返回的商品数据及其来源。

输出每个 UPC 的 `related|unrelated|uncertain`、理由及引用商品字段。
程序检查 ID 来自工具、引用实际存在，再核验库存、有效价格、数量和明确标签。
模型判断语义相关并不自动证明所有硬条件成立。

## 4. 整篮推荐与确认

`ModelBasketRecommender` 只接收：

- 每项通过语义审查及程序硬过滤的候选；
- 已确定的其他商品；
- 每项当前 active requirement、原用户要求和全局预算。

模型仅提议每项候选 UPC 或 null，并说明理由。
不得编造价格、标签或购物车操作，不能继续把历史首选名当成 fallback 的硬名称条件。
程序验证 UPC 属于该项候选池，并计算整篮包装数量、单价和总价。

后续数量设计补充：默认由模型先推荐，再调用专门模型步骤解释原始数量/单位与推荐包装。
输出 proposal/conflict/needs_clarification/insufficient_product_data，程序校验事实、正整数件数
和可信算术后展示整份方案确认。用户先选候选不是默认必经步骤，只有无法可靠推荐、
冲突/不确定或用户主动要求时才进入该分支。详见
[模型推荐与数量解释设计](product-and-quantity-interpretation-design.md)。
后续 v2 已接入该专门数量步骤；旧 v1 兼容路径不具备，未见商品语义准确性仍需独立评估。

返回 `awaiting_basket_confirmation`，用户可 accept 或对指定 requirement replace。
模型建议不等于购买授权；替换后生成新版整篮草稿，不能沿用旧批准。
当前执行范围仍是本地购物车，不扩展到真实账户写入或下单。

## 5. 缺货识别与逐项阶段切换

用户接受后，程序复查价格、库存与硬条件，再执行本地购物车操作。
只有确认首选 `out_of_stock` 且存在用户给出的有效 fallback，才执行该项
`phase=primary → fallback`。

转换必须：

1. 保存结构化缺货原因、来源与观察时间。
2. 清除失败 UPC 的当前选择及旧推荐批准。
3. 保留原话、修订、不变约束和其他商品状态，只重开受影响需求。
4. 重新计算目标购物篮与剩余操作，已有商品不重复加购或计价。

API/网络错误、详情读取失败、未知标签、价格变化不能冒充确认缺货。
缺少稳定工具错误码时，结构化失败原因与确认方法必须在实现中定义。
需要改变用户明确条件且无 fallback 时进入可恢复的替换询问；
用户明确答复后记录为修订，不能把沉默当授权。具体交互按统一合同 5.1 节执行。

## 6. 替代目标、检索恢复与第二轮审查

程序按已保存规则构造新的 active requirement：

- K16：其他奶，必须明确 dairy_free+nut_free。
- K19：用户已指定的 Colombian 咖啡，保留原数量与其他有效条件。
- K20：意面切到 Ditalini，酱切到 Tomato Basil；两个需求独立恢复。

首选名在这个阶段只作为历史/软偏好，不再成为替代商品的硬匹配要求。
查询可由保存的范围形成，必要时由模型建议有界搜索词，但实际工具调用由程序执行。
模型不得为了提高召回而扩大用户允许范围或删除硬约束。

恢复必须覆盖两种零候选情况：

```text
原始 search_products 返回 0 条
→ 在允许范围内有界改写查询

原始搜索非空，但语义审查/硬过滤后剩 0 条
→ 根据当前阶段和具体拒绝原因，在允许范围内有界扩大检索
```

重试次数、查询去重和模型/工具调用上限需显式定义，不得无限循环。

第二轮模型必须按 active requirement 审查新商品；程序再次验证证据和硬条件。
`tree_nut_free` 不能替代 `nut_free`，标签缺失保持未知，不能由模型补成合格。
API 错误走服务恢复，不转换成“商品不相关”或自动放宽条件。

## 7. 新草稿、历史候选与会话恢复

合格后由推荐模型提出新整篮，程序重新报价、生成新版确认。
接受后重新读取价格、库存和硬条件，再更新本地购物车并最终验证。
价格、库存或商品变化导致旧草稿失效时，不得沿用旧批准。

未选历史候选不永久屏蔽。用户返回选旧商品时，重新读取当前详情和核验当前约束，
生成当前版本选项，不复用旧 option_id、旧价格或旧库存。
暂时缺货与用户明确拒绝分别保存；库存恢复后可重新审查，明确排除由用户主动修订解除。

checkpoint 保存阶段、条件及其证据、库存观察、选择、候选历史、待答问题和全局状态。
恢复时检查当前事实与推荐版本，不能直接依靠历史批准执行。
具体候选历史与数量解释遵循另外两份已记录设计：
[候选历史](candidate-history-and-reselection-design.md)、
[商品与数量解释](product-and-quantity-interpretation-design.md)。

## 8. 建议修改范围

- `interactive_intent.py` / 提示词：结构化提取 primary/fallback/触发条件/来源。
- `choices.py`：逐项 phase、active spec、暂时缺货观察和候选历史。
- `interactive.py`：typed 失败原因、阶段转换、局部重开、旧批准失效和 checkpoint。
- `discovery.py`：按 active spec 搜索审查；过滤后零候选也触发有界检索恢复。
- `recommendation.py`：从当前阶段合格候选选 UPC 并说明理由，保持整篮条件。
- API / 模拟用户：可恢复的替换询问、来源明确的答复、新整篮确认。

上述是后续建议，不代表这些结构已经接入当前代码。

## 9. 验收与诊断要求

待执行测试：

- 覆盖 K16 与 K19 的 high/medium/low，替代授权不依赖提取描述的偶然措辞。
- K20 两项各自触发缺货，分别启用各自替代规则，保留已有鸡蛋/面包和已加入胡萝卜。
- 首选有货时不启用替代；改变明确条件且没有替代规则时暂停询问；
  模型自选商品缺货后可在原范围重荐，用户明确拒绝替代时不得自行换商品。
- API 错误、未知标签、价格变化不触发缺货阶段切换。
- 缺少明确 nut_free 证据或只有 tree_nut_free 时仍拒绝。
- 已有购物车与其他需求保持正确，整篮预算只计算一次。
- 价格/库存变化后重新核验、报价并确认；旧批准和过期 option_id 不可复用。
- 非空原始结果过滤为零时，有界搜索能找到允许的替代目标或正常停止。
- 历史未选候选可重新核验，checkpoint 恢复保留逐项阶段和规则证据。
- 冻结 benchmark 数据不为修复修改，购物代理不访问隐藏评分条件。

诊断分别记录模型语义误判、搜索漏召回、程序硬过滤原因和最终状态。
应能追溯每次查询与返回商品、每项审查理由/证据、每次过滤及阶段转换的依据，
不能将所有原因都仅记为 `no_candidates` 或 `hard_constraints`。
