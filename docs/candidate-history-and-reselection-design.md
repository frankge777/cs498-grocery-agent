# 历史候选与重新选择：设计依据

本文保留支线聊天确认的设计修正。后续 v2 已保存候选历史和暂时缺货观察，
并通过 select_history 接口重新核验历史候选；当前实现与剩余边界见
[运行说明](shopping-v2-runtime.md)。下文不代表完整自然语言历史选择/排除管理已实现。

## 核心区别

- 用户本轮未选择商品，或表示“这一轮都不满意”：不是永久拒绝其中每件商品。
- 用户要求“看看更便宜的”：更新软偏好，不自动建立排除名单。
- 商品缺货：记录有时间和来源的可用状态，不代表永久不再销售。
- 用户明确说“不再给我看 A”：记录明确排除；用户主动改口后可解除。

不设置默认永久生效的 rejected_upcs 黑名单。未选中、暂时缺货与明确排除
必须分别表示，不能都转换为同一种永久禁用状态。当前代码的
旧 v1 的 excluded_product_ids / 缺货排除机制较简单，保留兼容；
v2 暂时缺货不会写入永久排除集合，完整显式排除与解除接口仍待后续完成。

## 每项需求需要保存的信息

- 历轮候选及展示时的商品资料、查询词、候选轮次和读取时间。
- 当前软偏好与当前硬约束，保留用户原话和明确修订。
- 用户明确排除的商品、排除依据、解除记录。
- 当前选中的 UPC 和数量解释。
- 最近一次价格、库存、规格等商品事实的来源与读取时间。

历史记录保存当时看到的内容；它不是商品当前仍可购买的证明。

## 必须支持的循环

```text
第一轮展示 A / B
→ 用户希望看看更便宜的
→ 第二轮展示 C / D
→ 用户选 C
→ C 缺货
→ 重新考虑当前与历史候选
→ 用户可返回选择第一轮的 B
```

B 不能因为第一轮没有被选中而被永久屏蔽。恢复时可综合当前有效候选和
历史候选，按当前需求、偏好、明确排除情况和最新商品事实重新形成选择题。

## 历史商品重新选择的执行规则

1. 用户可表达“回到上一轮”“还是选 B”等意图；系统定位到历史候选的商品身份。
2. 重新调用商品详情，检查当前价格、库存、包装数量及所有硬约束。
3. 生成当前版本的新选择项或确认请求。旧 option_id 不能直接提交执行，
   旧库存、旧价格不能作为当前依据。
4. 若价格或包装变化影响数量解释或预算，重新计算并在必要时请用户确认。
5. 验证通过后才恢复为可执行状态；其他已确定需求继续保留。

## 偏好和限制的处理

- “最好更便宜”是软偏好：用户主动选择较贵的 B 可以接受，但仍检查硬预算。
- “绝不能超过 $5”是硬限制：选择 B 导致超预算时必须暂停，只有用户明确
  修改限制后才能继续，不能把选择 B 本身解释成同意增加预算。
- 用户主动恢复曾明确排除的 A 时，记录解除或修改排除的修订，不悄悄删除历史。

## 后续验证要求

验证多轮返回历史候选、缺货后恢复、临时缺货后重新有货、软偏好改变、硬预算
不被自动放宽、明确排除与主动解除、旧选项被拒绝，以及历史价格/包装变化后
重新确认。没有这些检查，不能声称历史候选循环已经完成。
